## Context

`localTriger` 已使用本地 NCNN 替代 `/ai/auto`，但 `LocalTriggerDetectionService` 当前将任意非空标签视为隐患，随后仍固定请求 `/ai/deep`。仓库已有 `info.json` 本地知识、`ResolvedHazardContent` 统一结果模型、模拟流式文本组件和网络状态工具，可在不新增页面或传输协议的前提下补齐离线详情。

本次变更涉及 NCNN 标签聚合、组合规则、详情来源路由、知识解析、页面展示和保存门禁。必须保持 JNI 入口、相机帧获取、在线 `/ai/deep` 协议以及结束巡检链路不变。

## Goals / Non-Goals

**Goals:**

- 用四条确定性组合规则判断本地隐患。
- 有网时继续以 `/ai/deep` 作为最终详情权威来源。
- 无网或明确连接失败时生成结构兼容的本地详情。
- 在线和离线结果复用相同展示、滚动、语音与确认交互。
- 离线隐患不调用保存接口，恢复网络后允许结束巡检。
- 将规则、知识解析和路由设计成可独立单元测试的纯逻辑组件。

**Non-Goals:**

- 不修改 NCNN 模型、阈值、JNI 接口或类别索引。
- 不替换 `/ai/deep`、`/ai/device`、场景隐患等其他接口。
- 不在应用内实现真实 SSE 服务，也不增加 `/ai/json` 网络端点。
- 不补传离线产生的隐患。
- 不改变 `standard`、`dataBackup` 的 HTTP `/ai/auto` 行为。

## Decisions

### 1. 使用纯逻辑组合规则评估器

新增 `LocalHazardRuleEvaluator`，输入标准化后的标签集合，输出规则命中列表及缺失标签。规则为：

- `负荷开关` 存在且 `T字按钮` 缺失。
- `液化石油气瓶` 存在且 `可燃气体报警器` 缺失。
- `燃气灶` 存在且 `熄火保护装置` 缺失。
- `室内消火栓箱` 存在，且 `水枪`、`水带`、`栓口` 中至少一个缺失。

“接口装置”固定映射到 `栓口（hydrant_nozzle）`，不使用建筑外部的 `水泵接合器（pump_connector）`。规则层不依赖 Android、Bitmap、JNI 或页面状态。

替代方案是继续按 `info.json.item` 做任意正标签匹配，但它无法表达保护装置存在时排除隐患，因此不采用。

### 2. NCNN 统一触发，详情来源按请求时网络状态分流

本地 NCNN 每轮仍返回完整去重 labels。隐患识别页只在规则命中后进入详情阶段：

- `SystemStateUtils.isNetworkAvailable()` 为真：请求 `/ai/deep`。
- 为假：直接解析本地详情。
- `/ai/deep` 发生 DNS、连接、超时等明确网络错误：回退同一帧、同一 labels 的本地详情。
- 鉴权失败、HTTP 协议错误、合法响应内容错误不回退，沿用在线失败提示。

网络状态在详情请求前即时判断，不在 Activity 启动时缓存，允许巡检过程中网络变化。

替代方案是在 Activity 内散布网络分支，改动更少但会扩大页面职责，因此不采用。

### 3. 本地知识解析输出统一结果模型

新增 `LocalHazardDetailResolver`，按规则标识或隐患编号从 `info.json` 获取等级、依据、编号和整改建议，生成 `ResolvedHazardContent(source = LOCAL)`。消火栓描述根据实际 `missingLabels` 动态说明缺少的配件；其他规则使用 JSON 描述。

离线文本按 `/ai/deep` 当前解析器支持的字段顺序生成：`隐患描述`、`隐患等级`、`主要依据`、`隐患编号`、`整改建议`。多条命中生成多个 `ResolvedHazardItem`。

不伪造 `task_id/content` SSE 事件，因为页面最终消费的是累积文本和 `ResolvedHazardContent`；伪造传输层只会增加无业务价值的复杂度。

### 4. 复用现有模拟流式展示

离线完整结果通过 `SimulatedStreamTextChunker` 和现有本地展示入口逐段显示。在线结果仍使用 `/ai/deep` SSE，并在完成后进入现有展示入口。两条路径不新增页面状态，不改变输入、滚动或语音规则。

### 5. 上传权限绑定到结果来源

离线详情必须携带明确的不可远程保存属性，而不是在用户确认时重新检查网络。`submitLocalHazardAndShowAdvice()` 对不可远程保存结果跳过 `pushHidDanger`，直接进入现有建议/返回流程；即使之后恢复网络也不补传。

结束巡检是否允许上传由结束时网络和现有企业巡检条件决定，不因本次会话曾产生离线详情而永久禁用，因此网络恢复后允许 `pushHidDangerEnd`。

## Risks / Trade-offs

- [单帧未识别到保护装置会产生误报] → 沿用现有置信度阈值和稳定帧机制，并对主对象与配件使用同一推理快照；不跨帧拼接标签。
- [`info.json` 现有 item 与新组合规则不完全一致] → 通过稳定规则标识或隐患编号解析知识，不再依赖 `item` 的任意正标签语义，并修正燃气报警记录映射。
- [系统判断有网但远端不可达] → 仅对可分类的网络连接错误执行本地回退，并记录路由和失败原因。
- [离线隐患未进入服务端记录] → 页面明确视为本地结果且不显示上传成功；这是需求指定边界。
- [多条规则同时命中导致详情较长] → 复用多隐患结构和现有滚动逻辑，按规则固定顺序输出以保证稳定测试。

## Migration Plan

1. 先增加纯逻辑规则、知识解析和路由测试。
2. 接入本地 trigger 输出与详情分流，不改变 HTTP provider。
3. 接入离线保存门禁并验证结束巡检仍可在恢复网络后上传。
4. 执行 `localTriger` 与 `standard` 单测和构建。
5. 真机分别验证在线、启动即离线、请求中断网和恢复网络结束巡检。

回滚时移除新详情分流并恢复 `LocalTriggerDetectionService` 原来的本地触发行为；模型资产和在线接口无需迁移。

## Open Questions

无。已确认“接口装置”对应栓口，且采用“离线隐患不保存、恢复网络后允许结束接口”的策略。
