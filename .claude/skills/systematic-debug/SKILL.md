# systematic-debug Skill

提供一套结构化的调试方法论，避免随机猜测，用系统化流程高效定位问题根因。

## When to Use This Skill

触发条件（满足任一即可）：
- 代码运行异常、报错、行为不符合预期
- 需要定位 bug 根因而非修复表象
- 面对复杂问题无从下手时
- 用户提到"debug"、"调试"、"排查"、"定位"、"bug"、"根因"
- 测试失败需要分析失败原因

## Not For / Boundaries

- 不适用于简单的语法错误（编译器/IDE 直接指出）
- 不替代代码审查或测试编写
- 不处理硬件故障或外部服务不可用（需要运维排查）

必要输入（缺失时需询问）：
1. 错误现象（报错信息、异常行为、期望 vs 实际）
2. 可复现的最小步骤或已知复现条件
3. 已尝试过的排查手段

## Quick Reference

### 调试 6 步法（MUST 按序执行）

```
Step 1: 复现 → Step 2: 缩小范围 → Step 3: 提出假设
Step 4: 验证假设 → Step 5: 确定根因 → Step 6: 修复+验证
```

### 1. 复现优先原则

| 可复现性 | 策略 |
|---------|------|
| 稳定复现 | 直接进入下一步 |
| 间歇复现 | 加大频率/记录触发条件/找模式 |
| 无法复现 | **暂停分析**，先做复现。不可复现的 bug 一切分析都是猜测 |

```
复现 checklist：
□ 用相同输入能触发？
□ 用相同环境能触发？
□ 减小/放大输入量能改变频率？
□ 加日志后频率是否变化？（Heisenbug 检测）
```

### 2. 二分定位法

将 Git bisect 思路推广到所有调试维度：

| 维度 | 二分策略 |
|------|---------|
| **代码范围** | 注释掉一半代码 → 哪半出错 → 继续二分 |
| **版本/commit** | `git bisect` 定位引入版本 |
| **输入数据** | 去掉一半输入 → 哪半触发出错 |
| **配置变更** | 回退一半配置差异 → 定位具体配置项 |
| **依赖版本** | 锁定一半依赖版本 → 定位出问题的依赖 |

### 3. 假设-验证循环

```
观察现象 → 提出最可能假设 → 设计最小实验 → 验证/推翻 → 更新假设

记录格式：
  H1: [假设描述] → 实验：[操作] → 结果：[验证/推翻]
  H2: [修正假设] → 实验：[操作] → 结果：[验证/推翻]
  → ...逐轮收敛
  Hn: 确认根因
```

不要同时测试多个假设，每次只验证一个。

### 4. 根因追溯（5 Whys）

每层追问"为什么"，直到无法继续：

```
现象: 用户登录超时
Why1: 请求没到达后端 → Why2: Nginx 返回 502
  → Why3: 后端服务挂了 → Why4: OOM 被杀
    → Why5: 内存泄漏，长时间运行后耗尽 → 根因

区分三层原因：
  直接原因（Direct Cause）：内存耗尽
  根本原因（Root Cause）：代码未释放连接池
  贡献因素（Contributor）：监控缺失，未提前发现
```

### 5. 差异调试（Diff-Driven）

当存在"工作版本"和"非工作版本"时：

```bash
# 代码差异
git diff working-commit..broken-commit

# 环境差异
diff <(env_on_working) <(env_on_broken)

# 配置差异
diff working-config.json broken-config.json

# 运行时差异
# 分别在两个版本加日志，对比执行路径
```

差异优先检查顺序：代码 > 环境变量 > 配置 > 运行时状态 > 依赖 > 并发

### 6. 日志驱动调试

**日志注入策略**：

```
关键路径埋点：
  entry: 函数入口，记录参数
  decision: 每个分支，记录条件值
  mutation: 状态变更前后，记录旧值→新值
  exit: 函数出口，记录返回值

性能热路径不要加同步日志，用 ring buffer 或采样
```

**信号-噪声分离**：

看日志前先明确"正常日志长什么样"，排除噪音再找异常。不要一上来就逐行读。

### 7. 变换-隔离法

逐一排除变量，每次只改一个：

```
1. 最小化输入 → 问题还在？
2. 简化配置 → 问题还在？
3. 去掉缓存 → 问题还在？
4. 串行化并发 → 问题还在？
5. 关闭优化 → 问题还在？
6. 换依赖版本 → 问题还在？
→ 排除所有无关变量后，剩余的就是问题域
```

### 8. 修复前自检清单

```
□ 我理解根本原因（不只是表象）了吗？
□ 修复方案是最小化的吗？（不引入无关改动）
□ 能写一个测试用例覆盖这个 bug 吗？
□ 修复可能影响哪些其他地方？（检查调用链）
□ 同类问题在其他地方也存在吗？（搜索相似模式）
```

## Examples

### Example 1: 二分定位 API 性能问题

**输入**: 某 API 偶尔超时，但不知道哪段逻辑慢
**步骤**:
1. 复现：构造 100 次相同请求，确认 15% 概率超时
2. 二分代码：在中间位置加耗时打点，分割为 A 段和 B 段
3. 超时请求中 B 段耗时正常 → 问题在 A 段
4. 继续二分 A 段 → 定位到一个数据库查询
5. 根因：缺少索引，数据量增大后慢查询触发了连接超时
**验收**: 加上索引后 1000 次请求无超时，P99 < 100ms

### Example 2: 假设-验证循环排查内存泄漏

**输入**: 服务运行 2 小时后 OOM，重启后恢复
**步骤**:
1. H1: 怀疑某缓存未设 TTL → 实验：禁用缓存 → 仍泄漏 → 推翻
2. H2: 怀疑连接未关闭 → 实验：打印连接数 → 连接数正常 → 推翻
3. H3: 怀疑大对象常驻 → 实验：heap dump 分析 → 发现 50 万个未回收的闭包
4. 根因：事件监听器注册后未解绑，每次事件创建新闭包
**验收**: 添加解绑逻辑后，运行 24 小时内存稳定

### Example 3: 差异调试定位环境问题

**输入**: 测试环境正常，生产环境报错
**步骤**:
1. 差异对比：代码相同 → 数据库版本不同（测试 PG 14，生产 PG 13）
2. 差异对比：SQL 中用到了 PG 14 新增语法 `JSONB || JSONB`
3. 验证：在本地 PG 13 执行相同 SQL → 复现报错
4. 根因：代码中使用了高版本特性，低版本不支持
**验收**: 替换为兼容语法后生产正常，CI 增加 PG 13 测试矩阵

### Example 4: 变换-隔离法排查并发 bug

**输入**: 高并发下偶发数据错乱，低并发正常
**步骤**:
1. 串行化：单线程运行 → 正常
2. 去掉锁：注释掉部分 synchronized → 更频繁出错
3. 隔离：逐个检查共享变量 → 发现一个 HashMap 在多线程下无保护
4. 根因：ConcurrentHashMap 的 putIfAbsent 与后续 get 之间存在 TOCTOU 竞态
5. 修复：使用 computeIfAbsent 原子化整个操作
**验收**: 100 并发线程运行 1 小时无错乱，单元测试覆盖竞态场景
